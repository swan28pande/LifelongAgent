# Closest work to `memory_v3/` and what may supersede it

Research cutoff: **2026-09-26**. This assessment uses the current `memory_v3/` implementation and its imported `memory_v2` store/summarizer. The older `paper.tex` describes earlier versions and was not treated as the specification. The project has no root `CONTEXT.md` or populated `docs/adr/` at this cutoff. [Plan](plan.md) · [Evidence ledger](evidence.md) · [Sources](sources.md).

## Assessment in brief

**APEX-MEM is the closest overall research paper.** It already combines a retained, time-grounded history of extracted conversational facts/events, structured SQL-backed queries, raw evidence, and an agent that selects multiple retrieval tools. Its graph, evidence links, entity resolution, and temporal validity model are richer than the local flat ledger. It does not report the local calendar summary chain or tests of recurring, committed preference choices. The broad claim “append-only temporal memory plus a multi-tool SQL reader” is therefore already covered; the complete local package is not demonstrated to be identical to APEX-MEM. [APEX-MEM, §§3–4 and 6](https://aclanthology.org/2026.acl-long.749.pdf).

**Chronos is the closest match for dated structured events plus raw-turn retrieval.** It builds an event calendar and a separate raw-turn calendar, then lets a ReAct agent query each through semantic and exact lexical tools with date filters. It omits the local preference/fact taxonomy, SQL timeline, and week-to-lifetime summaries. [Chronos, §§3–4](https://arxiv.org/html/2603.16862).

**TiMem is the closest match for the temporal summary hierarchy.** It consolidates segment, session, day, week and monthly profile memories, then routes retrieval by query complexity. It does not expose the local typed, append-only preference ledger or documented exact raw-turn lookup. [TiMem, §§3–4](https://aclanthology.org/2026.findings-acl.1091.pdf).

No reviewed paper or product demonstrates strict **end-to-end empirical supersession** of this exact implementation. Their published scores use different splits, answer models, judges, retrieval budgets and ingestion schedules. Several works already cover most of the **architectural** territory and have broader public evaluations; this is a stronger conclusion than any numeric ranking against the local runs.

## What the local system actually contributes

The write path extracts one day's committed **choices** (a specific value selected from a recurring category), stable facts, and one-off events in one LLM call. It keeps distinct dates of repeated choices rather than collapsing them, normalizes near-duplicate value spellings, stores dated rows and raw five-turn chunks, and can rebuild week → month → year → lifetime summaries. The read agent can request exact SQL date ranges, date-specific raw turns, semantic raw or summary search, and direct summaries. Live turns remain in context until end-of-day `flush()`. [Ingestion](../../memory_v3/ingest.py) · [Prompts](../../memory_v3/prompts.py) · [Tools](../../memory_v3/tools.py) · [Summarizer](../../memory_v2/summarizer.py).

Two scope details matter. “One LLM call per day” applies to **extraction**; updating summaries invokes additional calls. “Append-only” applies to the v3 structured write path; derived summaries are replaced on rebuild. A structured record has one date for when a choice or event *applies*; the SQL row does not separately preserve the conversation's observation date. That is less expressive than systems with separate event and ingestion times, especially for future plans or corrections. [Agent](../../memory_v3/agent.py) · [Store](../../memory_v2/store.py) · [Graphiti/Zep, §2.2](https://arxiv.org/html/2501.13956).

## Ranked closest works

| Rank | Work | Exact overlap | Key distinction | Assessment |
|---|---|---|---|---|
| 1 | [APEX-MEM](https://aclanthology.org/2026.acl-long.749/) (ACL 2026) | Time-grounded, retained fact/event history; SQLite; raw evidence; agentic SQL plus hybrid search. | Event/entity graph with source spans, canonicalization and validity; no reported calendar preference-cycle summaries or fixed daily extraction budget. | **Substantially solves the generic temporal structured-QA architecture** and is the strongest novelty counterexample. |
| 2 | [Chronos](https://arxiv.org/html/2603.16862) (2026 preprint) | Dated event index + raw-turn index; exact/semantic/date-filtered tools; iterative reader. | No comprehensive preference/fact ledger, SQL queries, or summary pyramid. | **Substantially solves the dual-store temporal retrieval problem.** |
| 3 | [TiMem](https://aclanthology.org/2026.findings-acl.1091/) (Findings ACL 2026) | Temporal levels through week and month/profile; consolidates user interests/preferences; adaptive recall. | Distilled leaves rather than exact append-only typed observations and raw-turn drill-down; no yearly/lifetime layers. | **Substantially solves the hierarchy/consolidation component.** |
| 4 | [Graphiti/Zep](https://arxiv.org/html/2501.13956) (2025 preprint) | Raw episodes, evolving temporal facts, entity/community summaries, hybrid search. | Bitemporal graph invalidates old edges; no demonstrated agentic SQL reader or calendar cycle summary. | **Earlier temporal-state and provenance counterexample; stronger temporal representation.** |
| 5 | [HiMem](https://arxiv.org/abs/2601.06377) (2026 preprint) | Immutable raw episodes plus linked preference/fact/profile notes and a note-first reader with fallback to episodes. | Semantic notes can be updated or removed; no exact per-day choice series or calendar summary chain. | **Closest to the hybrid raw + typed-semantic memory layout.** |
| 6 | [REMem](https://arxiv.org/html/2602.13530) (ICLR 2026) | Dated episodic gists, triple facts and iterative time-aware tool retrieval. | Schemaless fact/gist graph, without v3's raw-turn lookup, normalized choice timelines or calendar summaries. | **Strong independent prior art for episodic graph + agentic temporal reasoning.** |

[THEANINE](https://aclanthology.org/2025.naacl-long.435/) (NAACL 2025) is an older, narrower but important counterexample to claiming that retaining old memories and reading linked temporal timelines is new. [H-Mem](https://aclanthology.org/2026.eacl-long.363/) indexes original turns in year/month/day and topic trees, while [HiGMem](https://arxiv.org/abs/2604.18349) links event summaries back to raw turns. Their distinctions from v3 are summarized in the evidence ledger.

## Systems to benchmark as practical alternatives

[Hindsight](https://arxiv.org/html/2512.12818) combines time-ranged narrative facts, experience records, derived observations, raw source chunks, and semantic/lexical/graph/temporal recall. Its “opinions” are the agent's beliefs, rather than dated observations of the user's committed choices. It is a broad reference for personalization and evolving state. [MIRIX](https://arxiv.org/html/2507.07957) is another broad system with a preference-containing core store, timestamped episodic summaries and agent-routed retrieval, but its core memory can be rewritten and it does not expose v3's choice timeline or calendar summaries. [Mem0's original paper](https://arxiv.org/html/2504.19413) described reconcile-in-place ADD/UPDATE/DELETE/NOOP memory. The newer [managed temporal release](https://mem0.ai/blog/the-token-efficient-memory-algorithm-now-has-temporal-reasoning) claims a single-pass ADD-only history and time-aware retrieval, making it a closer *current product* comparator; the repository's local OSS Mem0 runner is not that version. [PGMem](https://arxiv.org/html/2608.01708) is an adjacent 2026 paper for explicit evidence-backed preference-state transitions, but targets response personalization rather than exact-date QA.

[LangMem](https://github.com/langchain-ai/langmem/blob/main/docs/docs/concepts/conceptual_guide.md) is a useful implementation baseline for extraction, consolidation and search, but is a toolkit rather than a fixed temporal memory design; its managers can update or remove old memories. These systems demonstrate relevant capabilities, and several report strong benchmark results. Their documentation does not establish that they are strictly better at this project's **recurring daily choice and cycle** task, or at equal cost, on a shared protocol.

## Why published scores do not prove a winner

The repository evaluated only **one** public LoCoMo dialogue, conv-26 (199 questions), using Gemini 3.5 Flash and the original token-F1/abstention scoring. Agentic v3 got **0.460 overall**, or **0.557 excluding adversarial**; one-pass reading of its *same store* got **0.608 overall**, or **0.546 excluding adversarial**, with about one-eighth the answer-time LLM calls. The local OSS Mem0 comparison has an unequal context budget, and the two v3 readers use different answer prompts. Those confounds are acknowledged in the repo. [LoCoMo results](../../results/locomo/README.md) · [runner protocol](../../benchmarks/locomo/README.md).

Many outside LoCoMo memory scores cover **1,540 non-adversarial questions across 10 public conversations**, judged by an LLM, often with different backbones and retrieval budgets. APEX-MEM is an exception: its Table 1 includes adversarial questions and reports **88.88%** with GPT-5. Within that table's **non-adversarial** column, its GPT-4o reader gets **86.75%**, slightly below full-context GPT-4o at **87.52%**. That is an important qualification to treating its headline score as proof that its architecture dominates. Chronos and TiMem also use LLM-judge accuracy, not the local token F1. [APEX-MEM, Tables 1 and 3](https://aclanthology.org/2026.acl-long.749.pdf) · [Chronos, §4](https://arxiv.org/html/2603.16862) · [TiMem, §4](https://aclanthology.org/2026.findings-acl.1091.pdf).

The local synthetic run is narrower: **one user, 60 days, 67 questions**; v3 scored **0.478** by its LLM judge and **0/3** on pattern-identification questions. It does not currently substantiate a claim that the summary hierarchy reliably discovers periodic behavior. [Synthetic results](../../results/synthetic/v3/README.md).

## Novelty and remaining distinction

| Proposed claim about v3 | Prior-art status | Evidence / exact limit |
|---|---|---|
| Store old preference states instead of overwriting them. | **Already solved under multiple representations.** | [THEANINE](https://aclanthology.org/2025.naacl-long.435/) retains old event memories; [Graphiti/Zep](https://arxiv.org/html/2501.13956) records evolving graph states; [APEX-MEM](https://aclanthology.org/2026.acl-long.749.pdf) explicitly uses append-only facts. |
| Combine structured dated records, raw evidence, and a tool-calling reader. | **Substantially solved.** | [APEX-MEM](https://aclanthology.org/2026.acl-long.749.pdf) is near-identical at that level; [Chronos](https://arxiv.org/html/2603.16862) uses raw and event calendars with date-aware tools. |
| Build time-granularity summaries for lifelong recall. | **Substantially solved.** | [TiMem](https://aclanthology.org/2026.findings-acl.1091.pdf) covers segment/session/day/week/monthly profile; [H-Mem](https://aclanthology.org/2026.eacl-long.363.pdf) gives a parallel year/month/day retrieval tree. Their precise structures differ. |
| Keep each committed choice as a repeatable dated observation, infer its calendar rhythm, and retrieve the exact history together with period summaries at low write cost. | **Partially solved / exact full combination not found.** | APEX/Chronos/TiMem/PGMem each cover parts. No inspected primary source demonstrates the full combination on held-out periodic-choice questions under a shared budget. The local 0/3 pattern result means this remains a research **hypothesis**, not a demonstrated advantage. |

A publishable contribution would need a capability demonstrated beyond a combination of existing components. The most plausible target is **faithful repeated-choice histories and calibrated periodicity inference**: distinguish a regular routine from a transient change, answer past/current/next-choice questions with source dates, abstain when too few observations exist, and retain exact historical evidence. This is an inference about research positioning, not a claim that prior papers cannot do it.

## Decisive next experiment

1. Freeze one ingestion timeline, answer model/prompt, embedding model where feasible, retrieved-token budget, scoring judge, and cost accounting. Evaluate v3, one-pass v3, APEX-MEM, Chronos, TiMem, and at least one maintained practical system (Graphiti/Zep, Hindsight or managed Mem0). Pin versions and report any architecture that cannot be run with official code.
2. Run all 10 public LoCoMo conversations, all five categories, with both original token F1 and a common blinded semantic judge; add LongMemEval-S's temporal, update, preference, multi-session and abstention slices. Report per-conversation variance, retrieval evidence recall, write cost, answer calls/latency, and context tokens. [LoCoMo](https://github.com/snap-research/locomo) · [LongMemEval](https://github.com/xiaowu0162/LongMemEval).
3. Isolate the proposed distinction with a **held-out recurring-choice benchmark**: regular cycles, calendar-dependent routines, deliberate breaks, one-off experiments, reversion, corrections, and future plans. Score exact historical lookup, transition dates, cycle identification, next-choice prediction, and abstention separately. Include an equal-budget raw-RAG baseline and an exact SQL/time-series baseline. Replicate across users and schedules rather than using the existing three pattern questions. [PERMA](https://arxiv.org/html/2603.23231) and [PERSONAMEM](https://arxiv.org/abs/2504.14225) provide relevant preference-evolution tasks; [AMemGym](https://arxiv.org/abs/2603.01966) can test the live `converse()`/`flush()` regime. [DynamicMem](https://arxiv.org/html/2606.22877) is a harder multi-app extension, but needs an input adapter.

## Uncertainty and gap check

- No head-to-head with identical ingestion, reader, retrieval budget and judge exists; no strict empirical supersession claim is supported.
- APEX-MEM and Chronos papers describe close methods, but the inspected sources did not expose official code; reproducing them may require author code or a faithful reimplementation.
- Published papers rarely test **periodic committed choices** as a separate capability, so absence of a matching result is not proof of novelty or superiority.
- Different definitions of “preference” matter: v3 records a chosen value **on a day**, whereas many systems summarize enduring tastes or inferred persona traits. A fair benchmark must distinguish these.
- Alternate-term searches covered temporal/event-sourced/bitemporal memory, timeline-based dialogue, hierarchical consolidation, graph memory, user-profile evolution, and preference-change benchmarks. No closer all-component match was found, but this is a bounded literature search.
