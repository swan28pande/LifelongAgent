# Evidence ledger

Research cutoff: 2026-09-26. Claim statements below are source observations. Comparative judgments and ranking are in `report.md`. External numbers are the sources' reported results, not common-protocol replications.

## Local implementation and results

| ID | Supported observation and exact location | Qualification / limitation |
|---|---|---|
| L1 | `memory_v3/ingest.py` lines 122–177 runs one LLM extraction per day into `(entity, content, date, type, speaker)` records, where type is preference, fact, or event. Lines 218–329 consolidate value spellings, dedupe same-day repeats, and append records. Lines 338–345 index five-turn chunks. | The one-call statement describes extraction only. `memory_v3/agent.py` lines 145–147 can invoke additional LLM calls for summary updates; `memory_v2/summarizer.py` makes calls per level and recurring entity. |
| L2 | `memory_v2/store.py` stores structured rows and raw chunks in SQLite, indexes raw chunks and summaries in FAISS, and exposes exact date queries. `memory_v3/tools.py` exposes six read tools including structured date-range query, raw/summary semantic search, exact date lookup, and summary lookup. | Structured rows are append-only on the v3 ingestion path, but the store has a separate deletion API and derived summaries are upserted. One date column records the *applicable* date; the source conversation date is not separately retained on each structured row. |
| L3 | `memory_v2/summarizer.py` lines 1–20 and 194–650 build week → month → year → lifetime summaries, with per-entity preference transition analysis and hash-checked incremental rebuilding. | Recurring cycle rules are LLM-produced summaries, not a verified deterministic time-series model. |
| L4 | `memory_v3/agent.py` lines 206–264 keeps today's turns in context and ingests them on `flush()`. | Pending turns are process-local until flush; the paper-style benchmarks ingest recorded sessions rather than testing a long live deployment. |
| L5 | `results/locomo/README.md` lines 3–19 reports conv-26 only (199 questions), Gemini 3.5 Flash: agentic v3 token F1 0.460 overall / 0.557 excluding adversarial; one-pass v3 0.608 / 0.546; local OSS Mem0 0.557 / 0.452. Agentic v3 averages about eight LLM calls per question. | Lines 26–43 state one-pass v3 and Mem0 context budgets differ, the two v3 readers use different prompts, and adversarial abstention scoring penalizes some valid false-premise corrections. This run cannot establish full LoCoMo dominance. |
| L6 | `results/synthetic/v3/README.md` lines 6–17 reports 67 questions over 60 days: 0.143 token F1, 0.478 LLM-judge accuracy, and 0/3 pattern-identification successes. | One synthetic user and three pattern questions are weak evidence for reliable cycle inference. |

## Closest temporal and structured memory systems

| ID | Source evidence | Qualification / limitation |
|---|---|---|
| E1 | [APEX-MEM](https://aclanthology.org/2026.acl-long.749.pdf), abstract and §§3–4: temporally grounded entity/event property graph, append-only facts linked to raw-turn evidence, and ReAct retrieval with entity lookup, read-only GraphSQL, schema inspection, and hybrid search. §3.3 tracks conversation timestamp and normalizes relative dates; facts retain source spans and confidence. | Strong overlap with v3's dated records plus SQL/search tools. The paper does not describe week/month/year/lifetime recurring-preference summaries or fixed once-per-day batch extraction. Graph construction uses multiple LLM stages (§6.2). |
| E2 | [APEX-MEM](https://aclanthology.org/2026.acl-long.749.pdf), §6.2/Tables 1, 3, 4: paper reports LoCoMo 88.88% with GPT-5 reader and LongMemEval 86.2% with Claude 4.5 Sonnet under LLM judges. It reports tool ablations from 77.19% (schema/entity tools) to 79.45% (+SQL) to 87.00% (+Search), using Claude 4.5 Haiku. | LoCoMo graph construction uses Claude 4.5 Sonnet and Haiku; max 40 read tool calls; some baseline numbers come from other reports. In Table 1's **non-adversarial** column, GPT-4o APEX is 86.75% versus full-context GPT-4o at 87.52%; the all-category APEX value of 86.35% is not directly comparable to the full-context row, which omits adversarial items. Appendix F calls its append-only versus eager-update comparison **indirect**, not a controlled ablation. |
| E3 | [Chronos](https://arxiv.org/html/2603.16862), §§3.1–3.4: subject–verb–object events with normalized start/end date ranges and aliases, separately indexed raw turns, query-specific retrieval instructions, and a ReAct loop with semantic and exact lexical tools over events and turns. | It deliberately avoids a comprehensive user-fact graph (§3.1). It has no explicit per-category preference history, SQL store, or period-summary pyramid. |
| E4 | [Chronos](https://arxiv.org/html/2603.16862), §4/Tables 1–3: paper reports 92.6% with GPT-4o and 95.6% with Opus 4.6 on 500 LongMemEval-S questions using an LLM judge. | Some baseline figures use different backbones or judges; event-calendar ablation is on 116 questions, not 500. No official repository was linked in the inspected paper. |
| E5 | [REMem](https://arxiv.org/html/2602.13530), §§3.1–3.2: hybrid graph with dated episodic gists, fact triples and agentic iterative retrieval, including temporal filters, aggregation and ordering. §3.1 explicitly says it preserves gists and facts even when contradictory. | These sections document retrieval of gists and facts, **not original raw dialogue**. It lacks v3's normalized preference observations and calendar hierarchy. Its §4 benchmark includes full 1,986-question public LoCoMo plus other reading-comprehension data; evaluation metrics differ from APEX and local v3. |
| E6 | [THEANINE](https://aclanthology.org/2025.naacl-long.435/), §2: retains event memories instead of removing old ones, links temporal and causal timelines, and expands retrieval to linked history. | An earlier counterexample to novelty of history preservation or timeline-based recall; its §3–4 task is future response generation on MSC and Conversation Chronicles rather than v3-style SQL QA. |
| E7 | [Zep/Graphiti](https://arxiv.org/html/2501.13956), §§2.2–2.3: raw episode nodes, extracted entity/fact relations, event and ingestion timestamps, conflict-aware invalidation, and entity/community summaries. §4.3/Table 2 reports 71.2% on LongMemEval-S with GPT-4o answerer/judge and about 1.6k retrieved tokens. | Superseded relations retain history but old edges have `invalid_at` mutated (§2.2.3), so this is not strictly append-only. Community summaries differ from calendar summaries. The paper predates current [Graphiti code](https://github.com/getzep/graphiti) and does not demonstrate v3-style SQL tool routing. |
| E8 | [Mem0's 2025 paper](https://arxiv.org/html/2504.19413), §§2–3: standard Mem0 reconciles facts with ADD/UPDATE/DELETE/NOOP; graph version tracks entity relations. | Current [managed Mem0 temporal system](https://mem0.ai/blog/the-token-efficient-memory-algorithm-now-has-temporal-reasoning) says its newer single-pass ADD-only path retains temporal history and reports 92.5% on 1,540 non-adversarial LoCoMo questions. This is a vendor-reported managed-platform result; the local repo evaluates an OSS top-10 path, not that system. |
| E9 | [Hindsight](https://arxiv.org/html/2512.12818), §§3–4: extracted narrative facts and experiences retain temporal ranges, entity links and evidence; retrieval combines semantic, lexical, graph, and time signals. [Official docs](https://github.com/vectorize-io/hindsight/blob/main/skills/hindsight-docs/references/developer/api/documents.md#chunks) document raw source chunks. | Its “opinions” are the agent's subjective beliefs (§§5.3–5.5), **not dated observations of the user's committed choices**. No calendar preference-cycle pyramid is documented. Paper §7.3 imports some external baseline scores using a different judge and leaves retrieval-token placeholders; its headline scores are not direct v3 comparisons. |
| E10 | [PGMem](https://arxiv.org/html/2608.01708), §§4–5: provenance edges tie episodic events to short-lived persona state and longer-lived traits; explicit support/contradict/shift relations represent evolving preferences. | More specific preference evolution than flat records, but it targets preference-aligned response generation with small backbones, not exact-date SQL QA or calendar summary retrieval. |

## Closest hierarchical and episodic systems

| ID | Source evidence | Qualification / limitation |
|---|---|---|
| E11 | [TiMem](https://aclanthology.org/2026.findings-acl.1091.pdf), §§3.1–3.3: segment → session → day → week → monthly updated profile; daily/weekly consolidation identifies interests and preferences; query-complexity-aware recall combines semantic/BM25 leaf search with ancestor expansion. §4.1/Table 1 reports 75.30% on 1,540 non-adversarial LoCoMo questions with GPT-4o-mini and recall k=20. | Leaves are distilled factual segments, and the paper does not document exact original-turn retrieval or a typed append-only preference ledger. §6 identifies missing typed structures. It lacks yearly/lifetime summaries. |
| E12 | [HiMem](https://arxiv.org/pdf/2601.06377), §§2.2–2.4: immutable timestamped episodes retain dialogue segments, while linked notes encode facts, preferences and profiles; note-first retrieval can fall back to episodes. Table 1 reports 80.71 GPT-Score and 34.95 token F1 on non-adversarial LoCoMo. | Notes can be updated/deleted. No calendar period summary chain or exact preference observation sequence is shown. Paper's judge and model protocol differs from local v3. |
| E13 | [H-Mem](https://aclanthology.org/2026.eacl-long.363.pdf), §§3.1–3.2: selected original turns are leaves in both year → month → day and topic trees; an LLM routes temporal/semantic queries. Table 1 reports 72.47% binary judge and 47.57 F1 on LoCoMo. | The time tree is an index, not week/month/year/lifetime summaries; there is no typed preference ledger. |
| E14 | [HiGMem](https://arxiv.org/pdf/2604.18349), §§3.1–3.3: event summaries and fact sheets are linked to raw turn nodes, then an LLM selects turns through events. Tables 1–2 show better F1 than A-MEM in four of five LoCoMo categories and fewer retrieved turns, but lower temporal F1 (0.34 vs 0.39). | Event groupings are semantic, not calendar summaries; no dated preference time series. This comparison is within its paper, not against local v3. |
| E15 | [NEMORI](https://arxiv.org/pdf/2508.03341), §§3.2–3.4: an episode retains a narrative, retrieval cue, embedding, and original turns; semantic insights consolidate across episodes and top retrieved episodes can expose raw turns. | Semantic insights may be merged/replaced; no exact preference history or calendar hierarchy. Its LoCoMo Table 2 excludes adversarial questions. |
| E16 | [MIRIX](https://arxiv.org/html/2507.07957), §§3.1–3.3: six routed stores include persistent user preferences in core memory and timestamped episodic summaries with dialogue excerpts; a chat agent searches the stores, then chooses targeted retrieval tools. §4.1 excludes adversarial LoCoMo questions and uses GPT-4.1 as judge. | Core memory can be rewritten once full (§3.1); episodes are event summaries rather than a typed, append-only daily choice ledger. No calendar period-summary chain or exact SQL timeline is shown. Its reported 85.4% LoCoMo score does not share the local evaluation protocol. |
| E17 | [LangMem's official concepts](https://github.com/langchain-ai/langmem/blob/main/docs/docs/concepts/conceptual_guide.md) distinguish semantic, episodic and procedural memories; its managers extract, consolidate, update and remove memories, and its store supports keyed access, semantic search and metadata filtering. | LangMem supplies composable memory primitives rather than a specified dated preference ledger, raw-turn index, period-summary hierarchy and SQL reader. Its reconciliation model does not guarantee retention of every superseded preference observation. |

## Evaluation fit and counterevidence

| ID | Source evidence | Qualification / limitation |
|---|---|---|
| B1 | [LoCoMo official repository](https://github.com/snap-research/locomo) exposes the public `locomo10.json`; the repository's local copy contains 10 dialogues and 1,986 QA items, 446 adversarial. [Original paper](https://aclanthology.org/2024.acl-long.747/) Appendix B/Table 5 describes a broader dataset. | A result labeled only “LoCoMo” may use a different split, omit adversarial items, or use a different judge. |
| B2 | [LongMemEval paper and repository](https://github.com/xiaowu0162/LongMemEval) define 500-question settings with preference, knowledge-update, temporal, multi-session and abstention abilities. | The S, M and oracle settings have different history lengths and evaluation conditions. |
| B3 | [PERSONAMEM](https://arxiv.org/abs/2504.14225) abstract: over 180 user profiles, histories up to 60 sessions, 15 tasks and evolving profile-based response selection. | This tests personalization decisions, not exact dated recall or periodicity by itself. |
| B4 | [PERMA](https://arxiv.org/html/2603.23231), §4.3: event-driven preferences and temporally placed zero-memory, in-time and post-intervention tasks, including interactive preference-conditioned use. | Designed for preference emergence and interference, not a direct drop-in replacement for LoCoMo QA. |
| B5 | [DynamicMem](https://arxiv.org/html/2606.22877), abstract, §§3–5: 15-month multi-app trajectories with evolving attributes/habits/preferences and quarterly checkpoints. | Input is structured app activity, not v3's conversational transcript; a connector would be needed. The paper reports no evaluated system jointly retains stable facts and updates changing facts. |
| B6 | [AMemGym](https://arxiv.org/abs/2603.01966), abstract: on-policy simulated-user interactions with state evolution and write/read/utilization diagnostics. | More directly tests `converse()` + `flush()` behavior than static replay, but uses a simulated environment. |
